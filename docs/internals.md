# Workflow View — внутреннее устройство

Полная логика плагина для будущих сессий. Всё проверено тестами (35+) и живыми ранами.

## Слои

- **src/worker.ts** — единственный воркер: весь CLI-доступ, снапшоты, instantiate,
  хендлеры панелей/редактора. Спавнит `bash -c` (trusted-worker), терминалов сам не держит
  (кроме спящего хелпера `--from`).
- **src/panel.html** — HTML-панель: полный DOM, `--orca-*` тема, состояние в plugin storage
  (`html.*`), кэш снапшота `state.snapshot`. Мост не трогает — читает готовое.
- **src/editor/{entry,sync,core,ui}.ts** — граф-редактор `.workflow.yaml`; decode/emit через
  ТОТ ЖЕ парсер (`../workflow`), edit-сессия с merge-by-id.
- **src/{workflow,yaml}.ts** — схема шаблона и толерантный YAML-парсер (ручки правок:
  хвостовые запятые, dash-less flow-строки — «id: plan-review,» валидно).
- **src/bridge.ts** — CLI-раннер + терминал-хелпер.
- **src/protocol.ts** — единственный источник типов запросов/событий.

## Мост (bridge.ts)

- `run(cmd)` = `execFile('bash', ['-c', cmd])` напрямую из воркера. Никаких sendText.
- Ошибка несёт **полный stderr** на исключении (`error.stderr`) — матчеры ретраев смотрят
  его: обрезка сообщения когда-то выкинула код `no_active_sender_terminal` у длинной
  команды, и материализация умирала.
- Ретраи: `no_active_sender_terminal` → повтор с `--from <хелпер>`;
  `stable_pane_required` → пересоздать хелпер и повторить.
- Хелпер: host-`terminal.create` (фоновый, без вкладки) в воркспейсе пина;
  кэш по путям проекта (ротация идентичности фенсила раны — `consumer_fenced`).
- `pin(path)` ставит проект (из project.current / instantiate / template.list);
  фоновый refresh НЕ пинит (иначе ротация посреди джобы).
- **Адреса проекта — всегда настоящие** (`realPath`, симлинки разрешены). Адрес приходит из
  реестра Орки (`orca repo list`) и может идти через симлинк: при переезде на другой логин
  старый домашний каталог оставляют симлинком на новый. Орка же ищет воркспейс по строковому
  совпаданию адреса и симлинки не разрешает — `path:<симлинк>` даёт `selector_not_found`, и
  мост не может создать хелпер: с виду «ран не поднялся» на команде `terminal create`.
  Каноникализация в трёх местах: реестр при определении проекта, `pin` (а поиск воркспейса у
  хоста сравнивает адреса как каталоги) и адрес, который панель передаёт в поднятие рана.
  Канонический адрес годится для селекторов ВОРКСПЕЙСОВ (они зарегистрированы по настоящему
  адресу); для селектора РЕПОЗИТОРИЯ он не годится — там реестр со старой записью, поэтому
  репозиторий выбирается по id (см. Instantiate).
- **Отчёт об отказе — это ответ Орки, а не команда.** `causeOf(error)` берёт stderr CLI: в
  `Command failed: bash -c …` первым идёт текст команды (с целым брифом у `agent launch`), и
  настоящая причина оказывалась за краём обрезки.
- Пустые каталоги/файлы маскируют exit-код как старый echo (`; true`) — см. loadSpecialists.

## Схема шаблона

- Шаги верхнего уровня **авто-цепляются** по порядку (steps без deps ← предыдущий).
- `worker:` — ссылка на карточку (slug = имя файла, вложенность не важит, shallow wins).
  Легаси-имён нет: `specialist`/`spec`/`when`/`after` отвергаются парсером.
- Карточка `.orca/workers/<...>.yaml`: `agent, model, effort (с model), swarm {enable, limit},
  fallback[], prompt`. Каталог моделей — из `agent-model-catalog.db` (models.list),
  воркеры редактора подбираются по покрытию слогов (workers.listSmart — фокус врёт).
  **swarm** — рой: параллельные инстансы воркера в одном ране. `enable: true` + `limit: N`
  (limit без значения = без потолка). Отсутствие swarm = рой выключен. Исполнение
  совещательное: строка в брифе координатора («РОЙ: … до N одновременно»); движок не
  троттлит.
- **Фазы подшагов** (4, дефолт обязательного `before_end`, опционального `after_end`):
  - `before_start` — до старта воркера: deps=внешние родителя, **родитель ждёт**;
  - `parallel` — вместе с воркером: deps=внешние, родителя не ждёт, **следующий ждёт пару**;
  - `before_end` — после работы воркера, до отчёта: deps=[родитель], **следующий ждёт
    подшаг** (верификация внутри шага; «отчёт финален после подшага» — правило брифа);
  - `after_end` — после отчёта: deps=[родитель], ничего не ждёт (RUN:-механика).
  Реализация: materialize + пост-аугментация `closersOf` (parallel+before_end держат
  следующий шаг; after_end-дети исключаются; **не добавлять юниту саму себя** — цикл!).
  Блок без воркера: закрывают обязательные НЕ-after_end дети.
- `optional: true` — условность: координатор пропускает «не той задаче», не начат не
  блокирует. Панель рисует «пропущен» (серое кольцо с чертой, «ПРОПУЩЕН», строка гаснет),
  когда флоу прошёл его позицию (maxPassedOrder по order-штампам).
- `gate` на шаге/блоке (барьерный гейт — на первый следующий шаг); `on_reject {goto,
  max_rounds}` — вердикт-цикл; `{{objective}}/{{repo}}/{{base_branch}}/{{worktree}}`.
- **Контейнер проверок** — блок `sub:` без воркера (`tests`, `code-review`): итог блока =
  отчёты всех запущенных проверок. Реджект блока = `request-changes` или падение **любой
  запущенной** проверки (в списке наблюдения materialize все не-after_end дети, optional
  включён — запущенная optional-проверка, нашедшая блокеры, возвращает работу). Dep на
  контейнер разворачивается в обязательные НЕ-after_end дети — **все-optional блок рвёт
  цепочку**, одна проверка обязана быть required. Формулировки фаз для детей контейнера —
  «от соседей по блоку», не «от воркера» (coordinatorBrief знает hasWorker).
  В coordinator-режиме агрегацию ведёт координатор (правило брифа 3a: замечания всех
  отклонивших — в один раунд; после доработки перезапускаются только отклонившие/падавшие);
  в autopilot-режиме — циклы движка (loop 2 вердикты, loop 4 падения, loop 3 перепроверка
  через `rechecksDue`; кэш `verdicts[taskId]` чистится при каждом worker-start — иначе
  вердикт новой попытки не парсится).

## Instantiate («Поднять Run»)

Порядок в коде: **проверка конфигурации → `run-create` → задачи и гейты → ворктри → бриф →
координатор**. Пункты ниже — по темам, а не по хронометражу.

0. **Конфигурация — до `run-create`.** Карточки читаются заранее (`loadSpecialists`): у шаблона нет
   карточки воркера или карточка координатора не разбирается → `failed` с именем недостающего/битого,
   ран не создаётся — в истории не остаётся пустой ран без задач.
1. `worktree create` (base-branch из формы; «ветка (опц.)» → `--branch` — точное имя без логина, пусто → `<логин>/<имя-ворктри>`) → воркспейс рана = сессия.
   - **Репозиторий — по id** (`repoSelector`: адресу проекта через `realPath` ищем репозиторий в
     `orca repo list` и берём `id:<id>`). `--repo path:` строково сверяется с реестром Орки, а
     реестр может знать проект по другой записи того же каталога (переезд: старый дом — симлинк) —
     тогда `repo_not_found`. id от записи адреса не зависит.
   - **Имя ворктри**: одноимённый воркспейс, занятый живым раном (сверка по НАСТОЯЩЕМУ пути
     воркспейса — displayName может не совпадать с папкой, а у рана без ворктри путь выводится из
     имени и не должен занимать имя) → суффикс `-2`, `-3`; воркспейс без ранов → продолжаем в нём,
     без создания.
   - **Отказ создания останавливает подъём** (`failed` с ответом Орки): создание и проверка
     «ворктри появился в списке» стоят ДО перехватчика запуска координатора — внутри него отказ
     глушился, и панель получала «готово» с советом поднимать водителя вручную в несуществующий
     ворктри. Суффикс имени пишется в `auto.<runId>.worktreeName` сразу — по нему стартуют воркеры.
2. ран + задачи: спеки пишутся в `/tmp/wfv-<job>-<step>.md`, `task-create --spec-file`;
   каждая задача штампуется `order` (позиция в topo) — **task-list перемешивает строки**,
   панель сортирует по штампу;
3. бриф → `<ворктри>/.orca/coordinator-brief.md` (роль переносима: run-use + cat);
4. координатор — **CLI `orca agent launch`** в ворктри рана (host-вариант теряет промт
   при медленном буте); верификация тайтла + 1 ретрай; `coordLaunch.bootWaitMs` — шов.
   Агент, модель и effort — из карточки координатора (см. ниже): `--agent … [--model …
   [--effort …]]`, `--effort` только вместе с `--model`.
5. AutoState `auto.<runId>`: driver=coordinator, worktreePath (для сессионной привязки),
   children (taskId→parent/step:), tasks (агент/модель/fallback/order), optionals.
6. Цель из формы = опциональный ЗАГОЛОК; бриф велит координатору **всегда** открыть чат
   уточнением (цель/описание/скоуп), собранную постановку переслать планировщику
   (`send --to dispatch:`).

## Координатор (правила брифа)

- Немедленный `run-use`; шаги строго по флоу; фазы названы по именам шагов;
- факты: из отчётов — дословно следующим воркерам; RUN:-подшагу — точный список вопросов;
- цикл доработки = `task-update pending` + `worker-start` заново с замечаниями;
  **task-create запрещён** (раундовые задачи мусорили хвостом);
- optional пропускает по сути задачи; гейты = стоп-человеку; эскалация только в чат;
- агент-алиас/модель/effort прописаны в строке шага брифа (не гадает по списку агентов).

### Карточка координатора — по id шаблона

Один координатор на флоу; карточка выбирается **по соглашению имени**, поля в шаблоне нет
(`coordinatorFor`): `coordinator-<id шаблона>` (шаблон `test-design` → `coordinator-test-design`);
такой нет — общая `coordinator`.

- **Замена целиком.** Специализированная карточка заменяет общую: агент, модель, effort — свои,
  поля общей не наследуются. Модель из формы рана («модель (опц.)») — умолчание для ШАГОВ без
  своей модели, координатора не касается. Карточки координатора нет вовсе — агент из «агент по
  умолчанию» формы, модель — агента.
- **Текст.** Специализированная карточка вкладывается в бриф блоком «РОЛЬ И СПЕЦИФИКА ЭТОГО
  ФЛОУ» — обязательным и главнее правил брифа во всём, что касается смысла флоу; команды движка
  координатор берёт из раздела «Действия». Общая карточка в бриф **не вкладывается**: её правила
  уже живут в брифе, а второй список с расхождениями хуже одного — правка текста общей карточки
  ни на что не влияет (подсказка об этом — в форме карточки менеджера «Воркеры», под slug).
  Плейсхолдеры в тексте карточки координатора не подставляются: заголовок, репозиторий и ворктри
  бриф называет сам.
- **Битая карточка** (не разбирается) — подъём останавливается до `run-create`, ошибка называет
  карточку (`coordinatorCardChecked`): иначе ран молча пойдёт с общими правилами вместо
  специфичных. Без текста — не ошибка: так для флоу задают только агента или модель.
- `run.brief.refresh` собирает бриф по той же карточке — пересобранный файл несёт её текущий текст.

## Статусы и иконки — канон (не менять наощупь)

Источник статусов — движок оркестрации (`tasks.status`): `pending`, `ready`,
`dispatched`, `completed`, `failed`, `blocked`. Всё остальное ниже — ПРОИЗВОДНЫЕ
панели; каждая имеет ровно одно правило и одну иконку.

### Иконки панели (одна легенда на весь ран)

| Иконка | Значение | Где бывает |
|---|---|---|
| ✅ зелёная галочка (кольцо) | готово (succeeded) | шаги, подшаги, блоки |
| 🔴 красный крест (кольцо) | провал шага ИЛИ отклонено (succeeded + VERDICT: request-changes у попытки) | шаги, подшаги, блоки |
| ⏳ янтарный спиннер | работает (dispatched) | шаги, подшаги, блоки |
| 🕐 жёлтые часы | готов к запуску (ready) | ТОЛЬКО шаги и подшаги; у блока статуса ready НЕ БЫВАЕТ |
| ⏸ серые часы | ожидает (pending/queued/blocked) | шаги, подшаги, блоки |
| ⊘ серый круг с диагональной чертой | ПРОПУЩЕН (панельная производная, см. ниже) | шаги, подшаги |
| 🔒 замок янтарный | гейт ждёт ответа (флоу дошёл: удерживаемая задача blocked и её прочие зависимости закрыты) | строки гейтов |
| 🔒 замок серый | гейт впереди (ещё не дошли) | строки гейтов |
| 🔓 замок зелёный открытый | гейт решён | строки гейтов |

Цвета фиксированы (НЕ тема-переменные — в тёмных темах акценты не читаются):
ok `#3fb950`, fail `#f85149`, amber `#d29922`, gray `rgba(139,148,158,…)`,
нейтральная точка `#8b949e`.

### Производная «готов к запуску» vs спящий ран

Пока в ране ничего не запускалось и не завершалось (нет dispatched/succeeded/failed),
ready рисуется СЕРЫМИ часами — рон спит, суеты нет. Первый старт/финал включает
жёлтые часы для ready.

### «Пропущен» — два источника, одна иконка

Иконка ⊘, в выполненные не входит, из участников блока исключается — для обоих случаев.

**1. Явное решение человека — `skip` в гейте.** Шаг закрыт через гейт с опцией `skip`
(механика ниже). Метка «ПРОПУЩЕН (решение гейта)», трейс под шагом серый
(в движке задача completed — но зелёным он быть не должно).

**2. Производная панели.** У задачи НИ ОДНОЙ попытки (нет её taskId в workers снапшота) +
статус pending/ready + флоу уже прошёл её позицию (есть succeeded с большим order) +
(задача optional ИЛИ это проверка блока — parentTaskId начинается с `step:`).
Попытка была (в т.ч. рераны) — пропуском не станет никогда. Метка «ПРОПУЩЕН».

### Пропуск через гейт: `skip` и `on_skip`

```yaml
- id: tc-review
  worker: tc-reviewer
  gate:      { question: 'Пачка ТК одобрена — заводим в Аллюр?', options: [approve, request-changes, skip] }
  on_reject: { goto: tc, max_rounds: 3 }   # отклонено → назад
  on_skip:   { goto: commit }               # пропущено → вперёд
```

- `skip` — **явное** разрешение в `gate.options` (дефолт — только approve/request-changes):
  не всякий шаг можно осмысленно пропустить, решает автор шаблона. Кнопка в панели
  «skip — пропустить [→ шаг]».
- Пропускается шаг, который гейт **держит** (следующий за шагом с гейтом — тот же перенос,
  что и сам гейт). Без `on_skip` — только он и его подшаги; с `on_skip.goto` — всё до
  целевого шага не включая его.
- Валидация (парсер и редактор — одна): `on_skip` имеет смысл только при гейте с опцией
  `skip`; цель существует и лежит **строго после** шага с гейтом (сам шаг и предыдущие —
  ошибка). Назад ведёт `on_reject`.
- Механика движка (проверено на пробном ране): статуса «пропущен» у движка нет. Задачи
  закрываются `task-update --status completed --result "ПРОПУЩЕН: …"`. `gate-resolve`
  **заново вычисляет статус удерживаемой задачи и возвращает её в ready даже из completed** —
  поэтому порядок такой: (1) закрыть последующие задачи диапазона (их resolve не касается,
  движок разрешает закрывать при незакрытых зависимостях); (2) одной командой
  `gate-resolve --resolution skip && task-update <держимая> completed` — окно, в котором
  координатор может увидеть шаг готовым, короче одного запуска CLI (~0,4 с). Если
  координатор всё же успел стартовать шаг (отказ «Dispatch is active») — честная ошибка в панели.
- Истина о пропуске — только в storage плагина: `skipped.<runId>` = {taskId → {at, gateId, goto}};
  `task-list` поля result не отдаёт. `on_skip.goto` тоже знает только шаблон: при поднятии
  он пишется в `auto.<runId>.gates[taskId удерживаемой]`, снапшот отдаёт его в `gate.onSkip`.
- Координатор получает из ящика «Гейт решён из панели: skip» со списком пропущенных и
  точкой продолжения; правило 6a брифа запрещает запускать пропущенные задачи.
- Возврат: «↻ Перезапустить шаг» в дровере (задача completed — кнопка есть) сбрасывает шаг
  и хвост в pending и снимает запись о пропуске; удаление рана чистит `skipped.<runId>`.

### Агрегат блока (шаг без воркера, «Блок «id» — подшаги N/M»)

Участники — только НЕпропущенные дети:
- любая неудача (failed) → 🔴 блок провален;
- кто-то работает (dispatched) → ⏳ спиннер;
- все запущенные сдали (succeeded) → ✅ готово;
- всё остальное (ждём, частично готово, гейтнуты) → ⏸ серые часы.
Статуса «ready» у блока НЕ СУЩЕСТВУЕТ: блок — контейнер, его не запускают.
Счётчик: `сдали/запущенные`, пропущенные отдельным хвостом «(+K пропущено)».

### Трейс (пунктир флоу)

Пройденный участок зелёный, работающий — янтарный, проваленный — красный,
остальное — серое. Сегмент под замком гейта: решён — зелёный, ждёт (флоу дошёл) —
янтарный, впереди — серый, решён как skip — серый (пропуск не «пройден»). Сегменты и стрелки
шагов красятся теми же классами conn-ok/conn-run/conn-fail/conn-idle.

## Флоу кейсов и передача контекста

- **bugfix** — диагноз (bug-investigator) → гейт «диагноз верен?» → фикс (developer + стат-анализ) → ревью → тесты → коммит. Гейт после диагноза: человек подтверждает понимание бага ДО правок.
- **rework** — уточнение плана (planner + ресёрч optional) → ревью плана + гейт → разработка → ревью → тесты → коммит. Отличается от полного development-флоу стартом с уточнения, а не с нуля.
- **research** — параллельный блок исследователей + синтез отчёта (research-synthesizer).
- **Контекст (опц.)** в форме «Поднять Run»: строки вида «ворктри X, .orca/*-report.md, openspec/changes/<change>».
  Уходит в бриф координатора блоком «КОНТЕКСТ ОТ ПРЕДЫДУЩЕЙ РАБОТЫ» (читать первым делом,
  факты как данность, переспрашивать только пробелы) и хранится в runmeta — переживает
  пересборку брифа. Совмещается с повторным использованием имени ворктри (продолжение
  в том же воркспейсе).

## Панель

- **Ран привязан к сессии**: `session.workspace` (readContext + `workspace.list` у хоста,
  raced) → путь фокусного воркспейса; показывается ран с `worktreePath === sessionPath`
  (хранится в runmeta/AutoState; для легаси выводится `~/orca/workspaces/<repo>/<name>`).
  Воркспейс-лист именно через хост: мост бывает занят живым координатором, и привязка
  не должна зависеть от очереди терминала. Панель путь не обнуляет при сбое запроса —
  держит прошлый и показывает «не удалось определить воркспейс» с кнопкой Обновить.
- **Несколько ранов в одном ворктри** (перезапуски в то же имя): панель берёт новейший
  по `created_at` из orchestration.db (одним запросом в `runs.list`) и выводит строку
  «в этом воркспейсе ещё N ранов → Run history». При «Поднять Run» занятое имя ворктри
  авто-суффиксируется (`name-2`, `name-3`) — второй ран больше не подсаживается на чужую
  воркспейс/ветку молча.
  Селектора ранов нет; нет рана → «Поднять Run из шаблона» (+авто-таб).
- **Активность ранов в Run history**: `hasCoordinator` — координаторский чат жив
  (handle из runs сверен со списком терминалов Орки; мост занят — считаем живым,
  лучше лишний бейдж), `liveWorkers` — работающие воркеры ('starting'/'ready').
  Бейджи «координатор»/«воркеры: N» в строках; у рана с работающими воркерами ✕
  заблокирован (и run.delete отклоняет), у рана с живым координатором красная
  кнопка предупреждает, что чат останется без рана.
- Снапшот: воркер пишет `state.snapshot` в свой цикл (dedup без `at`); панель читает кэш,
  живой мост — только воркер. Обогащение: агент/модель/fallback/parentTaskId/optional/
  order из AutoState; вердикты попыток — см. ниже.
- Эффективные статусы: честные, без распространения гейтов по deps — гейтнутый шаг сам
  приходит со статусом 'blocked' (часы, «ждёт гейт»); родитель с работающими подшагами
  крутится сам (агрегат группы).
- Гейт держит старт шага — строка с замоком на нити ПЕРЕД удерживаемым шагом (замок
  янтарный закрытый / зелёный открытый), вопрос и состояние текстом («ждёт ответа» /
  «решён: <option>»); клик по строке разворачивает кнопки ответа, после resolve кнопки
  схлопываются. Воротный гейт блока — перед первым ребёнком.
- **Гейт на шаге = подтверждение результата шага**: материализация снимает его с юнита
  шага и вешает на первый следующий юнит (по deps; фолбэк — вход следующего шага по
  цепочке, у безродительских блоков deps бывают пусты). Автор объявляет гейт рядом со
  шагом, о котором вопрос; гейт на последнем шаге — ошибка (нечего держать). При
  нескольких наследниках держится первый (как у барьерных гейтов). Вместе с гейтом на
  удерживаемый шаг переезжает и `on_skip` шага (см. «Пропуск через гейт»).
- Попытки (GitLab-style): строки `#N агент·модель` в дровере, клик тоглит отчёт (все
  свёрнуты по умолчанию). **Вердикт попытки** парсится один раз (write-through при первом
  чтении отчёта + фоновое заполнение свежезавершённых) и живёт в снапшоте:
  request-changes → красный крест «✗ отклонена» (движковое succeeded — не показатель),
  approve → зелёная галочка.
- Трассер: единая пунктирная нить x=12 через весь шаг (главная строка стартует на 5px ниже
  иконки), подшаги подключены горизонтальным штрихом (зазор 2px), цвет по статусу строки
  (зелёный/янтарный/серый), z-index выше ховера, масок-фонов нет (любая тема).
- Иконки: кольцо-галочка (пройдено), спиннер янтарный (работает), часы серые (ждёт —
  и очередь, и гейтнутый шаг), перечёркнутое серое кольцо (пропущен), крест
  (отклонена/провал), плей (готов к запуску).
- Строка шага кликабельна целиком (тогл дровера; вложенные действия стопят всплытие,
  дровер поглощает клики); дроверы мульти-открыты.
- Удаление рана (✕): SQL-транзакция в orchestration.db (дети → runs), отказ при живых
  воркерах (`starting|ready`); мета плагина чистится.
- Прочее: строки координатора вне шаблона с id шага в названии вкладываются под шаг (⟲),
  остальные — хвост с пометкой; sticky-скоуп проекта (фокус без воркфлоу → проект
  последнего рана); шаблоны: фолбэк на библиотеку когда проект не определён, ↻ всегда.

## Редактор

- decode/emit = общий парсер; layout-комментарий `# workflow-view: layout id:x,y;…`
  (нет → autoLayout: слои топологические, высота слоя = самый высокий стек подшагов,
  подшаги стопкой справа, reject-дуги слева янтарным пунктиром).
- Инспектор: шаг (воркер+строка «карточка: агент·модель·effort» или «нет карточки»,
  агент, модель из каталога, fallback, гейт, on_reject, спека, подшаги, +Подшаг) и
  подшаг (те же + фаза-комбо 4 варианта, optional, delete).
- Менеджер воркеров: CRUD карточек, two-click delete, отказ при ссылках из шаблона.
- Живой пуш: правки → `templates.updated` (панель подхватывает без моста), дебаунс 800мс.
- Грабли: открытая вкладка после dev reload держит старый код; определение проекта —
  workers.listSmart по слогам (фокус/последний-ран врут).

## Известные ограничения

- `before_end`-порядок «отчёт потреблён после подшага» — правило брифа для координатора;
  движок гарантирует только зависимости (следующий шаг ждёт подшага).
- Вердикт при отсутствии строки VERDICT трактуется как approve (default).
- Панель/редактор после dev reload требуют переоткрытия (прод не страдает).
- CLI не умеет удалять раны — только наш SQL-путь; бэкапа базы нет (WAL, транзакция атомарна).
